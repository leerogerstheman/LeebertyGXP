# 验证指南 · Validation Guide

**本文档不是验证文件本身，而是编写验证文件时的输入清单。**

系统提供的是**证据与就绪度输入**；IQ/OQ 的签署、职责的指定、最终符合性判定，
仍须由站点具备资质的人员完成。

> ⚠️ 本软件按"现状"提供。投入 GxP 使用前，必须按贵司的计算机化系统验证程序
> 完成评估。未经验证即用于 GxP 记录，责任由使用方承担。

---

## 一、本系统的验证优势（请如实陈述，不要夸大）

| 特征 | 对验证的影响 |
|---|---|
| **零第三方运行时依赖** | 供应商评估范围极小——无需逐个评估 npm 包，无需评估传递依赖的漏洞与许可 |
| **无构建步骤** | 交付物即源代码；不存在"源码与运行版本不一致"的风险 |
| **单文件数据存储** | 备份、归档、恢复的对象明确；无数据库服务需单独验证 |
| **配置与代码分离** | 新增流程/检查表无需重新验证代码，只需评估配置变更 |
| **自带合规态势核对** | 12 项监管要求逐条给出**当前实际证据**，可直接摘入验证报告 |

**同时必须如实说明的局限：**
- 系统未经过第三方认证或独立审计
- 就绪度评分是排序工具，不是法规符合性判定
- 单实例架构，无高可用与多站点同步
- 依赖操作系统文件权限保护数据文件

## 二、建议的验证范围（基于风险，GAMP 5）

按 GAMP 5 软件分类，本系统属于**类别 5（自定义应用）**，但风险等级取决于用途：

| 用途 | 建议风险等级 | 验证深度 |
|---|---|---|
| 仅用于自查与就绪度跟踪（不作为 GxP 原始记录） | 低 | URS + 安装确认 + 权限确认 |
| 用于偏差/CAPA/变更控制记录（**作为 GxP 记录**） | 高 | 完整 URS/IQ/OQ + 审计追踪确认 + 备份恢复演练 |
| 替代纸质批记录或作为放行依据 | 高（需额外评估） | 上述全部 + 与现有体系的接口评估 + 更严格的数据完整性测试 |

**若作为 GxP 原始记录**，必须额外确认：
1. 审计追踪在真实使用场景下的完整性（不只是测试环境）
2. 电子签名与人员身份的绑定关系（账号发放程序）
3. 记录保存期限与归档程序
4. 停机期间的纸质记录程序与事后补录规则

## 三、用户需求说明（URS）要点

建议 URS 至少覆盖以下条目，每条都应可测试：

### 功能需求
- FR-01 系统应能记录偏差、变更控制、CAPA、OOS、GLP 研究偏离、GCP 方案偏离、
  供应商审计、数据完整性事件、药物警戒个例、召回/投诉，共 10 类流程
- FR-02 系统应能根据流程定义自动生成步骤清单，并按角色与顺序控制执行
- FR-03 指定步骤应强制电子签名后方可完成
- FR-04 系统应支持 SOP 等受控文件的版本、审批、定期审核与阅知确认
- FR-05 系统应提供法规检查表，支持逐条判定与客观证据记录
- FR-06 检查发现的缺陷应能转为受控的 CAPA 记录并保持关联
- FR-07 系统应维护人员培训资质矩阵，并回答"某人能否执行某 GxP 操作"
- FR-08 系统应维护设备确认状态、校准与维护计划，并预警超期
- FR-09 系统应能导出审计追踪、检查结论与质量记录清单

### 合规需求
- CR-01 审计追踪应只可追加，任何修改或删除尝试应被阻止并记录
- CR-02 审计追踪应能证明未被篡改（完整性校验）
- CR-03 电子签名应使用至少两个不同的识别要素
- CR-04 签名应包含签署人姓名、日期时间、含义与理由，并与记录永久关联
- CR-05 每个用户应有唯一账号，不得共用
- CR-06 权限应按角色分配，职责分离（执行者不得独自批准）
- CR-07 所有 GxP 记录变更应强制填写理由
- CR-08 会话应在空闲后超时，并告知用户登出原因
- CR-09 数据应可备份与恢复，恢复应可验证
- CR-10 记录的历史版本应可从审计追踪重建

### 非功能需求
- NFR-01 系统应在无互联网连接的车间/实验室环境运行
- NFR-02 系统不应要求管理员权限安装
- NFR-03 界面应支持中文与英文切换
- NFR-04 系统应能在 Windows 10/11 上运行

## 六、周期性回顾（GAMP 5 / Annex 11 §3）

建议**每年**进行一次系统周期性回顾，输入应包括：

1. **变更历史** —— 本系统的配置库变更（`seed/` 下的 JSON 变更记录）
2. **事件记录** —— 审计追踪中的 `system_error` 与 `access_denied` 条目
3. **权限复核** —— 用户清单、角色分配、离职账号处置（Annex 11 §12.1 要求定期复核）
4. **审计链完整性** —— 年度的完整性校验结果与封印记录
5. **备份与恢复** —— 恢复演练记录
6. **法规变化适应性** —— 新增/修订的法规条款是否已加入检查表库
7. **合规态势** —— 「合规态势」页面的当前评分与不符项
8. **用户反馈与缺陷** —— 使用中发现的软件问题及处置

回顾报告应形成文件并经 QA 批准。

## 八、已知局限（必须写入验证报告）

诚实陈述局限，比声称"完全符合"更经得起检查：

1. 本系统**未经过第三方认证或独立审计**
2. 就绪度评分与检查表是**辅助工具**，不构成法规符合性判定
3. 电子签名第二要素为 TOTP 或服务端挑战码，**不含生物特征**
4. 数据库文件**未做文件级加密**，依赖操作系统权限与磁盘加密
5. 单实例架构，**无高可用集群与多站点同步**
6. 检查表内容基于公开法规文本编制，**不保证穷尽所有条款**；
   站点应结合自身产品与工艺补充
7. 系统不管理**受试者身份信息**（GCP 场景仅记录受试者编号）
8. 打印输出为浏览器打印样式，**正式核证副本程序需站点另行规定**

## 九、快速自检命令

```bat
:: 端到端功能验证（62 项）
node test\e2e.js

:: 审计追踪完整性
node scripts\verify-audit.js

:: 生成检查前封印
node scripts\verify-audit.js --seal "2026 年度回顾基线"

:: 备份
node scripts\backup.js --label annual-review

:: 恢复演练验证
node scripts\backup.js --verify-only backups\<备份目录>\manifest.json
```

建议将 `verify-audit.js` 与 `backup.js` 配置为计划任务，并保留输出日志作为持续证据。
