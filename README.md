# LeebertyGXP

**让日常 GxP 义务可执行、可追溯、可审计。**

一个面向制药与实验室工作者的本地化合规工作台。覆盖 GMP、GLP、GCP、GVP、GDP、GPP、
GAMP 与数据完整性（ALCOA+）领域，把"文件规定应该怎么做"变成"系统推着你做、做错拦住、
做完自动留痕"，并在检查前就告诉你哪里有风险。

---

## 一、为什么这样设计

市面上多数"GMP 软件"是电子档案柜：把纸质表格搬进数据库，工人照样填错，QA 照样在
飞行检查前突击补记录。这样的工具不解决真问题，反而制造新的数据完整性风险。

本工作台基于三个判断：

**1. GxP 各领域的合规义务高度同构。**
偏差、变更控制、CAPA、OOS 调查、GLP 研究偏离、GCP 方案偏离、供应商审计——本质都是
"一条受控记录 + 一串有角色与签名门槛的步骤"。所以不能一个领域写一套代码。
**领域是数据，不是代码**：加一个新流程只需往 `seed/workflows/` 放一个 JSON 文件。

**2. 合规控制必须做进机制，不能靠自觉。**
审计追踪用哈希链实现，改库会被触发器拦死，绕过触发器改文件会被摘要校验抓出；
电子签名强制两个独立识别要素；所有 GxP 记录修改强制填写理由；
偏差的提出人不能自己关闭。这些是**代码强制**的，不是制度要求。

**3. 检查就绪度必须常态可见，而非临时突击。**
系统把法规条款变成可判定的检查项，把自检发现的每一项缺陷一键转成受控 CAPA，
并把未关闭缺陷、文件审核欠账、培训过期、校准超期、审计链完整性汇成一个就绪度评分，
直接列出**具体阻碍项**。

**4. 工作流要自己跑，不能等人来查。**
所有催办逻辑如果只在"打开页面时计算"，系统就是被动的。所以有一个后台进程常驻，
定时扫描超期记录、待签步骤、到期校准与培训，生成待办、升级严重超期、并在条件解除后
自动关闭——**不需要任何人打开页面**。

## 二、快速开始

### 只要双击一次

```
双击  LeebertyGXP.exe
```

**首次启动会自动完成全部初始化**，不需要先跑任何脚本：

1. 创建数据库、生成审计链密钥
2. 加载配置库（17 类流程定义、8 张检查表 285 项要求）
3. 创建演示账号（28 个身份，统一密码 `GxP-Demo-2026!`）
4. **生成演示数据集**（质量记录 + 4 个生产批次，含 GLP/GCP/GVP/GDP/GPP 各领域场景）
5. 校验审计链完整性 —— 通过

全流程约 **5 秒**，然后打开独立窗口显示**身份选择页**。第二次启动发现数据已存在，
只重载配置库，不重复生成。

托盘出现绿色对勾图标，工作台在**独立窗口**中打开（无地址栏，有自己的任务栏图标）。
托盘菜单可以：打开工作台、重新生成演示数据、校验审计追踪、备份数据、停止退出。

这个 exe 是 **18 KB** 的单文件，由 Windows 自带的 C# 编译器现场编译，
**窗口是本机的原生窗口**——WinForms 窗体 + 嵌入式 WebView2 渲染内核（微软 WebView2 SDK 绑定，随项目自带、可再分发），不打开任何浏览器。

<details>
<summary>为什么不是「先跑生成演示数据.bat，再跑 exe」</summary>

早期版本需要两次双击，而且桌面快捷方式上完全看不出第一步的存在。现在初始化
并入服务启动过程（`src/bootstrap.js`），因为**第一次打开时的体验就是产品本身**。

演示数据集的自动生成**受内置账号开关约束**：它写入的是虚构的偏差、CAPA 与签名，
进入真实审计追踪。生产实例绝不能发现里面有编造记录，所以
`GXP_BUILTIN_ACCOUNTS` 未开启时既没有虚构账号，也不会生成演示数据。

### 方式二：批处理启动

```
双击  start.bat
```

行为与 exe 相同，区别是**带控制台窗口能看到日志**（排查问题时用这个）。

- `start.bat` — 带控制台窗口
- `start-silent.bat` — 后台静默启动，日志写入 `logs/server.log`
- `start.bat 8790` — 换端口启动
- `stop.bat` — 停止后台实例
- `生成演示数据.bat` — 手工重新生成演示数据（通常不需要，首次启动已自动完成）

### 打开后你会看到什么

**程序自己的应用窗口，不是浏览器页面** —— 双击 `LeebertyGXP.exe` 或 `start.bat`，
打开的**是程序自己的原生窗口**：标题栏、图标、尺寸都是 LeebertyGXP 的，内容由嵌入式
WebView2（Windows 自带引擎）渲染，不是浏览器标签页。`start.bat` 与 `node src/server.js`
由服务器代开同一个窗口；`--browser` 或 SDK 文件缺失时才退回 Edge 的 `--app` 模式。
启动器同目录需要三个 WebView2 SDK 文件（`Microsoft.Web.WebView2.Core.dll`、
`Microsoft.Web.WebView2.WinForms.dll`、`WebView2Loader.dll`），构建时自动复制。

**第一屏是身份选择** —— 打开后先回答"你是谁"。身份按**职责范围**分三组：

| 分组 | 谁 | 登录后去哪 |
|---|---|---|
| **全域职责** | 系统负责人、内审员、质量保证负责人、QA 专员、质量受权人、培训协调员、外部检查员 | 进入**领域选择**（他们的职责本来就横跨全部领域，需要先决定看哪个） |
| **各领域负责人** | 主要研究者(PI)、临床监查员、专题负责人、QC 分析员、仓储物流员、注册事务专员… | **直接进入该身份的专属界面**，不再问领域 |
| **其他身份** | 未承担具体领域流程职责的岗位（如验证/计算机化系统工程师） | 进入领域选择 |

**点身份 → 输入密码 → 进入专属界面。** 每张身份卡上写明它会带你进入哪个领域
（"进入 GLP"、"进入领域选择"），所以选择是有依据的，不是进去之后才发现走错了。
密码是**真的校验**的：输错会明确提示"密码不正确"，而不是放行。

> **为什么共用一个密码却仍然要求输入？** 演示账号共用同一密码是**已标注的风险**
> （见第四节，21 CFR Part 11.300(a) 要求账号唯一）。但"点一下就进去"展示的是
> **去掉认证之后的授权**，而且一个可以跳过的认证步骤会教给读者"它是可选的"。
> 所以弹窗里给出演示口令作为提示，但**必须键入**才能进入。

**登录后：领域优先，一卡见流程图。** 身份已经确认，就不该再让身份卡挡路 ——
登录后回到领域选择页时，**8 张领域卡片在最前**（首屏内），身份卡退到下方作
「切换身份」用。点任意领域卡（如 GLP），**第一屏就是该领域的工作流程图**：
横向步骤、每步下方是责任人名片（姓名·职务·职责）、名片下方是他在这个岗位实际
持有的各项权限。这正是把"流程图看不见"的根因（领域卡埋在 2500px 之下）修掉后的样子。

**「领域与流程」页的最顶上就是流程图。** 侧边栏点"领域与流程"，打开后第一块就是
**工作流程图**：一行领域胶囊（GMP / GLP / GCP / GVP / GDP / GPP / GAMP / 数据完整性），
下面是当前所选领域的流程图级联——默认 GLP，点胶囊即时切换，整个过程无需登录
（流程图是参考模型，对所有人公开）。之后的身份卡与领域卡都是在这个之下的。

**领域选择对未登录者也可达** —— 匿名打开时身份卡在前、领域卡在后，**不必登录即可
浏览**每个领域的流程、岗位职责与权限矩阵：这些是**参考模型**，对所有人公开；记录
内容、人员信息与待办事项才需要身份。

**领域专属界面** —— 一个界面看全该领域：工作流程与责任分工（横向步骤，每步下面是
负责人名片，名片下面是他的各项权限）→ 流程清单 → 岗位职责 → 信息权限对应表 →
覆盖本领域的法规自查表。超出你职责范围的岗位名片会**灰显**，点击后说明拒绝理由。

**选择身份后看到的才是「我的待办」** —— 列出等待该身份提交/批复/核实/执行的条目，
按后果轻重排序（不是按时间），并明确标出哪些需要电子签名、哪些已经超期几天。
底部还有一块"你的权限范围"，说明这个岗位**不能**做什么 ——
这样操作工看到空的"待批复"页签时，不会怀疑系统坏了。

**操作工的日常是批次执行。** 演示数据里种了 4 个生产批次（`PRD-2026-0001..0004`），
分别停在**领料核对 → 投料与工艺参数 → 过程取样 → 放行评审**四个阶段：操作工登录后
待办里就是自己的批次步骤，点开记录逐项填写并完成（投料量、参数、取样点…），数据
与步骤关联；生产负责人独立复核（Annex 11 §12.1 拒绝作者自审）；QC/QP 作放行判定。
一条批次从头到尾——谁执行、谁复核、谁放行、哪里签名——都进审计链。

**新增用户（`系统管理员` 身份 → 用户与权限 → 新增用户）。** 只有系统管理员能建账号
（`user.manage`）。弹窗里除姓名/角色/部门外，还可以**声明该人员所属的 GxP 领域**：
声明后账号会出现在该领域的身份名单里，登录落点也按本人声明优先——一名只声明 GMP 的
新 QC 分析员，会落到 GMP 而不是按角色权重落到 GLP。初始密码可留空（之后用「重置密码」
签发临时密码），可勾选"首次登录必须修改密码"。**每个账号一张身份卡**：同一角色的两个
账号都出现在启动页（演示账号有讲解文案、新账号显示本人姓名），不会互相折叠。

不想要内置账号？用 `GXP_BUILTIN_ACCOUNTS=0` 启动，就会回到
"创建第一个管理员账号"的标准流程，同时**不会生成演示数据**。

### 命令行

```bat
node src\server.js                           :: 默认 127.0.0.1:8788，首次启动自动初始化
set GXP_HOST=0.0.0.0 && node src\server.js   :: 局域网共享（前面请配 HTTPS）
node src\daemon\monitor.js --once            :: 手工跑一次后台扫描
node scripts\seed-demo.js                    :: 手工重新生成演示数据（通常不需要）
```

环境变量：

| 变量 | 作用 |
|---|---|
| `GXP_BUILTIN_ACCOUNTS=1` | 演示账号，并开启首次启动自动生成演示数据 |
| `GXP_AUTO_SEED_DEMO=0` | 保留演示账号，但启动时保持空库 |
| `GXP_PORT=8790` | 换端口 |
| `GXP_MONITOR=0` | 不启动后台工作流进程 |
| `GXP_HOST=0.0.0.0` | 允许局域网访问（务必前置 HTTPS） |

### 环境要求

**只需要 Node.js 22.5 或更高版本**（依赖内置的 `node:sqlite`）。
**近乎零第三方依赖** —— 不需要 `npm install`，断网可运行。唯一的外部组件是微软
WebView2 SDK 绑定（启动器在本地编译时引用、随包分发）与 Windows 自带的 WebView2/Edge 引擎。
桌面启动器额外需要 Windows 自带的 .NET Framework C# 编译器（构建时）与 Edge（运行时）。

这不是技术洁癖，而是合规优势：在受验证环境里，每一个第三方包都需要单独的供应商评估
与变更控制（EU GMP Annex 11 §7.1）。运行时构件清单只有 **Node（自带）+ 微软 WebView2 SDK 绑定 + 系统引擎**，供应商评估范围远小于 Electron/npm 体系。

## 三、核心能力

### 后台工作流进程

| 能力 | 说明 |
|---|---|
| 定时扫描 | 默认每 5 分钟，覆盖 5 类条件（见下） |
| 幂等 | 重复扫描不产生重复任务、通知或审计条目；可随时重启 |
| 自动关闭 | 条件解除后自动关闭任务，**关闭动作本身也审计** |
| 升级 | 记录超期 30 天以上自动升级为 critical 并通知 QA 负责人 |
| 可归属 | 所有自动化写入标注为 `monitor` 系统 actor，**actor_id 为空**，一眼可分机器与人工 |

扫描的 5 类条件：质量记录超期、CAPA 缺有效性检查（ICH Q10 §3.2.2）、
校准与维护超期、GxP 培训过期与超期未完成、文件定期审核超期。

> **为什么这很重要：审计追踪的纪律。**
> 一个每周期都往审计追踪里写字的监视进程，会把账本淹在噪音里、毁掉它的证据价值。
> 所以这里的规则是**只审计状态变化，从不审计扫描动作**：任务创建一次、升级一次、
> 关闭一次，重复周期完全幂等。

### 合规内核（所有模块共用）

| 能力 | 实现 | 法规依据 |
|---|---|---|
| 审计追踪 | 只可追加，SHA-256 哈希链 + HMAC，密钥存于数据库之外 | 21 CFR Part 11.10(e)、Annex 11 §9 |
| 防篡改 | SQLite 触发器拦截 UPDATE/DELETE；链校验定位到具体断点 | ALCOA+、WHO TRS 1033 |
| 电子签名 | **两个独立识别要素**：密码 + 动态口令/一次性挑战码 | 21 CFR Part 11.200(a)(1)(i) |
| 签名要素 | 姓名、时间、含义、理由，并与记录永久关联 | 21 CFR Part 11.200(a)(2)-(3) |
| 权限控制 | 21 个角色、40+ 项权限，职责分离在服务端强制 | Annex 11 §12.1、ICH Q10 |
| 会话控制 | 空闲超时 + 会话绝对上限 + 失败锁定，并解释登出原因 | Annex 11 §12.3 |
| 修改理由 | 所有 GxP 记录变更强制填写理由 | 21 CFR Part 11.10(e) |
| 历史重建 | 任一记录的历史版本可从审计链单独重建 | ALCOA+ "Enduring/Available" |

### 领域模块

- **我的待办** — 按动作类型（提交/批复/核实/执行/审核）聚合所有来源，按后果排序，
  标明需签名项与超期天数，并解释本角色的权限边界
- **领域与流程** — 启动后第一屏就是领域选择，**一次点击**进入某个领域（不需要先登录）：
  1. **选领域**（`#/domains`）— GMP / GLP / GCP / GVP / GDP / GPP / GAMP / 数据完整性，
     每张卡片显示该领域的流程数、参与岗位数与可选身份数
  2. **领域专属界面**（`#/domain/GLP`）— 一个界面看全该领域：
     流程清单 → 岗位职责 → **工作流示意图**（本领域专属流程逐步展开，标注负责岗位、
     签名门槛与职责分离点）→ 信息权限对应表 → 覆盖本领域的法规自查表
  3. **选择身份**（同一界面内）— 按在本领域流程中承担的步骤数排序，
     点选即以该身份进入，随即看到他的待办与可执行操作
  4. **单条流程**（`#/workflow/GLP-SPEC`）— 完整工作流图、责任移交链、
     各参与者职责一览表、三态权限矩阵、21 项代码强制约束清单
- **质量记录** — 偏差、变更控制、CAPA、OOS 调查、GLP 研究偏离、GCP 方案偏离、
  供应商审计、数据完整性事件、药物警戒个例、召回/退货/投诉、生产批次执行，共 17 类流程
- **文件控制** — SOP/质量标准/验证方案/研究方案的版本、审批、定期审核、阅知确认
- **自查与就绪度** — 8 张检查表库（GMP 全章节、Part 11+Annex 11、数据完整性 ALCOA+、
  GCP ICH E6(R2)、GVP、GDP），逐条判定 + 客观证据强制 + 一键转 CAPA
- **培训与资质矩阵** — 谁可以做什么，培训有效期、GxP 关键课程门槛
- **设备与校验** — IQ/OQ/PQ 确认状态、校准与预防性维护；校准不合格自动停用
- **合规态势** — 把系统自身当作受审对象，逐条核对 12 项监管要求并给出证据

## 四、值得注意的设计决策

**职责写在图上，不放在悬浮提示里。** 工作流示意图的每个步骤下面直接列出负责岗位和
该岗位的职责文字。这一点修改过一次：最初职责只存在于 `title` 属性，鼠标悬停才显示——
而流程图恰恰是要截图、打印、贴到会议室墙上的东西，悬浮提示在那时完全失效。

**权限表必须是三态，不能是两态。** 「允许 / 不允许」会让界面与运行中的系统矛盾：
QA 负责人持有 `record.close`，但内核仍然拒绝他关闭自己写的记录。所以每个单元格有
第三种状态 **⚠ 有约束**，附原因与法规依据，取自 `src/domain/constraints.js` 中
21 项**代码强制**的约束。用户点开看到的就是服务端真正会做的事。

**参与者只能从既有岗位中选，不能在界面里创建。** 岗位不是标签，它绑定着 40+ 项权限
和服务端的步骤门。允许界面凭空造岗位，等于让界面声称一项服务端随后会拒绝的能力。
所以「添加参与者」是从 21 个既有岗位里勾选，改动真实生效，且无法创造不存在的权限。

**演示用统一密码是明确标注的风险，不是被默许的做法。** 内置的多角色演示账号共用
同一个密码，界面上用醒目的警示条说明这违反 21 CFR Part 11.300(a)「账号唯一」的要求，
并指出真实部署必须为每人签发独立凭证。演示便利性被保留了，但它没有被伪装成合规做法。

**校准不合格不自动放行。** 仪器校准判定不合格时自动置为"停用"，但**复校合格后不会
自动恢复在用** —— 恢复使用需要一条有理由的变更记录。因为"数据是在未校准仪器上产生的"
这件事需要有人正式评估影响，不能让系统悄悄放行。

**偏差提出人不能自己关闭记录。** `independentOfAuthor` 步骤会拒绝记录作者本人签署，
这是 ICH Q10 与 Annex 11 §12.1 职责分离的代码化。

**自查判定"存在缺陷"必须填客观证据。** 判定为"部分符合"或"存在缺陷"时，必须提供至少
10 个字的客观证据。无证据的负面判定在检查中不可辩护，所以直接在入口拦住。

**系统管理员不能作为 GxP 记录的唯一批准人。** 管理员可以维护用户与配置，但其账号
在质量角色审批场景下被明确拒绝。

**默认安全策略如实标注为"部分符合"。** 未正式批准默认策略的站点，"已文件化的安全策略"
检查项显示"部分符合"而非"符合"——这是诚实的自我评估，也是给检查员的正确信息。

**配置库保持为可编辑 JSON。** 工作流与检查表定义不打进可执行文件，因为站点需要能在
不重新构建的情况下新增 GxP 领域或调整流程。代价是 exe 需要同级 `app`/`seed` 目录。

**可见性按职能关系判定，不按行政级别。** 这一点推翻了最初的设计：原本打算把岗位分成
1 级（总负责者）、2 级（领域负责人），高级别可以查看低级别的一切。**这个设计被否决了**，
因为它与 GxP 的组织方式相反——质量保证之所以有价值，恰恰因为它独立于生产；QA 内审员要
审计生产负责人，而等级模型下这不可能。系统里已有三条代码强制约束建立在"按职能分离"之上
（记录作者不能关闭自己的记录、系统管理员不能作为唯一批准人、步骤只接受声明的角色），
引入等级会直接与它们冲突，并让审计追踪失去可辩护性：检查员问"为什么他能看下属的数据"，
按等级只能回答"因为他级别更高"，按职能却能回答"因为他是该流程的责任人，授权记录在案"。

替代方案是 `src/domain/visibility.js` 里的三档，由**职能关系**决定：

| 档 | 谁 | 能看什么 |
|---|---|---|
| `cross_domain` | QA 负责人、QA 专员、内审员、质量受权人、培训、外部检查员 | 跨领域的岗位人员 |
| `own_area` | 有专职领域的岗位 | 本领域全部岗位人员 |
| `public` | 其他（含系统管理员） | 只有岗位名、职责、权限 |

**每一条拒绝都带理由**，并由服务端随负载下发（`visibility.decisions`），前端只渲染判定
结果、不做权限推断。理由是硬要求：合规工具里一句无解释的"不行"教不会任何人，只会被绕过。
灰色名片点击后弹出的对话框会说明规则、给出理由、并列出**哪些内容仍然公开**。

**系统管理员不因技术权限获得可见范围。** 管理员持有全部权限，能维护整个实例，但不承担
任何 GxP 流程职责，因此在领域页上看到的所有岗位名片都是受限的。技术访问权与"有权阅读
他人的 GxP 工作"是两件事。

**领域限定的身份入口，由配置推导而非手工维护。** 最初把"被标注了该领域的流程"当作
"属于该领域"，于是 CAPA、偏差、变更控制、供应商审计这些横跨 4–6 个领域的流程污染了判断，
GVP 名下列出 17 个岗位，领域限定形同虚设。修正为**只按领域的专属流程**判断，再加一份
**显式声明**的贯穿性职能。这里刻意没有用启发式推导：曾试过"出现在跨领域流程里的岗位即
贯穿性职能"，结果 CAPA 的步骤包含生产操作工，推导得出"生产操作工属于 GCP"——启发式分不清
"管理质量体系的岗位"和"出现在恰好跨领域的流程里的岗位"。

**内审员不得审计自己承担职责的领域。** 服务端强制（`inspections.createInspection`），
越界返回 `SELF_AUDIT_NOT_INDEPENDENT` 并说明补救方式（由其他内审员主导，或改由 QA 负责人
以管理评审形式进行）。**被拒绝的尝试本身也写入审计追踪**——一次未遂的自审是关于质量体系
的发现，即使什么都没改变。QA 负责人审自己的领域不受限制，那是管理评审，本就该允许。

**外部检查员的访问是限时的，且到期后自动失效。** `users.access_expires_at` 在**登录时和
每个请求**都校验（会话可能很长，只在登录时检查会留下敞开的门）。到期账号自动标记为
`expired` 并记录原因；登录被拒时给出明确说明而非让用户误以为密码错误。

**导出审计追踪本身是一条记录。** 查看一个页面受会话约束，把审计追踪复制出系统则不受约束，
且副本无法收回。所以每次导出都记录：谁导出的、多少条离开、导出时用的过滤条件——这是回答
"有多少数据在系统之外、是谁拿走的"的唯一方式。记录在**生成负载之前**写入，因此生成后传输
中断的导出依然留痕。

★ = 核心模块

> ⚠️ **`.bat` 文件必须保持纯 ASCII，不要加中文。**
>
> `cmd.exe` 按控制台**当前代码页**逐字节读取批处理文件。两种失败方式：
>
> 1. 文件含 GBK 中文，但控制台被切到 UTF-8（`chcp 65001`）→ cmd 的读取偏移
>    中途错乱，开始执行注释和字符串的碎片，屏幕刷出一片
>    `'xxx' is not recognized as an internal or external command`。
> 2. 文件含 UTF-8 中文，但控制台停留在代码页 936 → 中文显示为乱码。
>
> 纯 ASCII 在 GBK、UTF-8 和所有旧代码页下**字节完全相同**，因此天然免疫任何代码页。
> 这样启动器就可以安全地先执行 `chcp 65001`，让 Node 进程以 UTF-8 输出中文
> （与网页界面编码一致）。
>
> **所以：所有面向用户的中文都写在 `src/server.js` 的启动横幅里，不写在 `.bat` 里。**
> 修改批处理时请确认文件仍为纯 ASCII + CRLF。网页与 `src/` 则一律使用 UTF-8，
> 两者互不影响。

## 六、数据与备份

**所有数据都在 `data/` 目录：**

| 文件 | 内容 |
|---|---|
| `gxp.db` | 业务数据与审计追踪 |
| `audit-chain.key` | 审计追踪哈希链密钥 |

> ⚠️ **`audit-chain.key` 必须与 `gxp.db` 一同备份。**
> 密钥丢失或与数据库不匹配，审计追踪将**永远无法校验**，且无法修复。

```bat
node scripts\backup.js                        :: 备份
node scripts\backup.js --label pre-upgrade    :: 带标签
node scripts\backup.js --verify-only <manifest.json>   :: 恢复演练
node scripts\verify-audit.js                  :: 校验审计链
```

`--verify-only` 会做**完整的恢复演练**：先校验字节完整性（在打开文件之前），
再打开备份副本验证哈希链。这个顺序是刻意的——SQLite 仅打开文件就会重写文件头，
先打开再算哈希必然不匹配。

生产环境请每日自动备份，并定期执行恢复演练，留存记录
（21 CFR Part 11.10(c)、EU GMP Annex 11 §7.2）。

## 八、自检

跑全部 8 个套件：

```bat
node test\run-all.js
```

`npm test` 等价。之所以把 `node` 形式写在前面：Windows 默认的 PowerShell 执行策略
会挡住 `npm.ps1`，而 `node` 不受影响。也可以只跑一部分：

```bat
node test\run-all.js e2e explorer
```

单独跑某一个套件：

```bat
node test\e2e.js           :: 62 项  核心引擎、签名、权限门、审计链
node test\monitor.js       :: 27 项  后台进程扫描规则与幂等性
node test\inbox.js         :: 42 项  待办聚合与动作分类
node test\explorer.js      :: 48 项  领域工作流视图、三态权限矩阵、参与者管理
node test\assets.js        :: 90 项  浏览器 DOM、责任级联、受限名片、CSS 类完整性
node test\firstrun.js      :: 18 项  首次启动自动初始化与幂等性（空目录 → 可用实例）
node test\audit-roles.js   :: 38 项  可见性模型、内审员独立性、外部检查员限时与导出留痕
node test\identity-flow.js :: 29 项  身份优先的启动流程、密码校验、各身份的落点
node test\operations.js    :: 18 项  生产批次执行、操作工待办、新增用户与账号生命周期
```

共 **372 项**检查，9 个套件。`explorer.js`、`assets.js` 与 `identity-flow.js` 会启动
真实服务器与真实浏览器（Edge headless，通过 CDP）验证界面，因此也覆盖「视图文件已
定义但未被 index.html 引用」这类不会抛错、只会导致白屏的问题。没有安装 Edge 时，
这些套件会打印 `skipped` 而不是失败。

`run-all.js` 会为每个套件**剥离继承来的 `GXP_*` 环境变量**。这不是洁癖：多数套件不设
任何环境变量、直接继承 shell，所以本机导出的 `GXP_DB_FILE` 会让 `e2e.js` 偏离它自己
的临时数据库，并在 200 毫秒内失败且不给出有用信息。`GXP_EDGE` 是唯一的例外，因为它
是合理的机器级覆盖。

`assets.js` 中的一项检查值得单独说明：它比对视图使用的每个 CSS 类是否都在
样式表中定义。缺失的类不会抛异常，只会静默渲染成无样式块——这类问题在所有
其他测试全绿的情况下依然会造成界面损坏。

`audit-roles.js` 测试的是**不会自己报错的规则**：可见性判定漂移了，界面看起来
照常工作；自我审计限制停止生效了，只表现为一次被允许的检查；到期校验失效了，
只表现为一次正常的登录。这三者破坏时都不产生任何异常，所以每条都用真实调用
断言，而不是相信代码写对了。其中一项还**断言了边界本身**：外部检查员不能重算
审计哈希链（`audit.verify` 不授予），这是组织的技术完整性操作，检查员接收结果
而不是执行它。

`assets.js` 里另有一类检查针对**位置而非存在性**：流程示意图曾经渲染完全正确、
元素断言全部通过，却因为排在第四块、位于六千五百像素长页面的四千像素处而
「看不见」。只有断言它在第几块、距顶部多少像素才能发现这类问题。

```bat
node scripts\verify-audit.js --record DEV-2026-0001   :: 单条记录版本历史
node scripts\verify-audit.js --seal "飞检前封印"       :: 生成完整性封印
node scripts\audit-coverage.js                        :: 各 GxP 领域内容覆盖审计
node scripts\screenshot-explorer.js                   :: 真实浏览器截图（需先启动服务）
```

## 九、这个项目是什么，以及它不是什么

### 9.1 定位：技术演示与参考实现，不是经过验证的系统

**本项目是技术演示与参考实现，用于说明一套 GxP 工作台可以怎样设计。**
它**没有经过软件验证**（GAMP 5），没有 URS、没有 IQ/OQ/PQ 方案、没有需求-测试
可追溯矩阵、没有验证总结报告。

这一点必须说清楚，因为后果是具体的：**用于产生或保存 GxP 记录的计算机化系统，
其自身必须先经过验证。** 用未经验证的软件产生受监管记录，本身就是一条偏差。
所以本项目**不得**直接部署到受监管的生产质量体系中。要那样用，需要先按你自己
的质量体系完成验证——`seed/` 下的配置库可以复用，验证工作不能省。

**MIT 许可证授予的是著作权意义上的使用许可，不是适用性声明，也不是合规声明。**
详见 LICENSE。

### 9.2 演示数据是虚构的

演示数据集中的企业（`华东制药（演示）`）、人员姓名、批次号、偏差与 CAPA 内容
全部虚构，仅用于展示工作流。**不包含任何真实企业的数据。** 首次启动生成演示数据
需要显式开启内置账号（`GXP_BUILTIN_ACCOUNTS=1`），默认关闭时不会写入任何虚构记录。

### 9.3 内置账号共用密码是已标注的风险

不得共用」的要求，界面上以醒目警示条说明。真实部署必须为每个用户签发独立凭证。

双要素签名（§11.200）**默认已开启**：签名需要密码 + 一次性挑战码两个独立识别要素。
只有在本机演示、需要减少操作步骤时才用 `GXP_SIG_2FA=0` 关闭——关掉它就不再满足
§11.200(a)(1)(i)，界面的合规态势页会如实标记为「未满足」。
